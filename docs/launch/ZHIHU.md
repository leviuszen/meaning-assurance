## 标题

```text
为什么两个 Coding Agent 都说“完成了”，仍然不能算验证？
```

## 开头

你的 Coding Agent 自信地说：“任务完成了。”

你真的相信吗？

如果不信，谁来反驳它？另一个 Agent、测试系统，还是你继续坐在终端前，和同一个
Agent 争论到它给出一个更让人安心的回答？

更反直觉的问题是：当两个 Agent 都说“看起来没问题”时，那究竟是证据，还是同步
的自信？

## 生产答案与批准答案是两种权力

Coding Agent 的核心优势是快速生产候选结果。但生产能力不应自动带来批准权。

传统软件工程至少会区分：

- 实现者；
- 测试证据；
- 审查者；
- 合并权限；
- 最终责任人。

如果把这些角色重新压回同一个 Agent 对话，工程流程看起来变快了，但信任问题没有
消失，只是被语言流畅度遮住了。

## 第二个 Agent 为什么仍然不够

第二个 Agent 可以提供价值，但“一致”本身不是证明：

1. 两个 Agent 可能读取了同一份不完整材料。
2. 第二个 Agent 可能没有独立运行测试。
3. Reviewer 可能把“没有看到证据”误写成“证明不存在”。
4. 两个模型可能共享类似的训练偏差和提示上下文。
5. 即使 Finding 正确，最终接受仍可能涉及风险与取舍。

因此真正需要保存的不是“几票同意”，而是：

```text
谁提出了什么主张
→ 它看到了什么证据
→ 哪项结论被挑战
→ 哪项得到确认或驳回
→ 哪项仍不可检验
→ 最终由谁接受
```

## Meaning Assurance 的答案

Meaning Assurance（AI 对抗审计助手）是一套本地优先、以文件为载体的 Coding
Agent 证据核验与对抗复审机制。

它提供：

- 有边界的任务包；
- 隔离实现 worktree；
- 冻结并哈希的复审材料；
- 第一轮独立审查；
- 第二轮只针对争议项；
- `confirmed`、`rejected`、`duplicate` 和 `not-testable` 裁决；
- 不自动合并；
- 人类最终接受。

## 一个刻意让双方都出错的 Demo

仓库包含一个无需 API Key 的确定性 Demo。Worker 声称完成，但证据显示漏跑一项
检查并修改了范围外文件；Reviewer 同时提出一项过度结论和一项缺乏证据的性能判断。

最终结果不是“Reviewer 胜利”，而是：

```text
2 confirmed · 1 rejected · 1 not testable
Final acceptance: BLOCKED
```

这才是对抗复审的意义：不仅约束 Worker，也约束 Reviewer。

## 必须承认的边界

这套机制不保证正确，不是操作系统沙箱，也不是法律或合规审计。冻结证据仍可能不
充分，Moderator 也可能判断错误。仓库公开的真实案例属于第一方 dogfooding，不是
独立验证。

它提供的不是“永远正确”，而是一条更容易检查、追问和拒绝的证据链。

## 结尾

委托工作，不等于交出决定权。

当 Coding Agent 说“完成了”时，我们不应该只问它是否自信，而应该检查它留下了
什么、谁挑战过它、哪些结论被证据支持，以及最终接受权还在不在人手里。
